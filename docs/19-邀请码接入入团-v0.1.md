# 邀请码接入入团 v0.1

这一版把[入团申请与成员审批](18-入团申请与成员审批-v0.1.md)里最后一个“看起来能用、实际没接上”的环节补上：社团后台生成的邀请码，终于可以真的拿到手机端入团；停用、过期或用完的码，也会被同一条共享接口拒绝。

- 日期：2026-11-22
- 范围：`mock-api/`、`admin/` 邀请码页、`mobile/` 登录与入团
- 数据：邀请码和成员申请都在本地 Mock API 进程内存
- 状态：可点击原型，未接真实账号、短信、实名认证或防刷

## 1. 这一版解决什么

在成员审批跨端之后，邀请码本身仍然是断的：

- 社团后台的邀请码页读写的是前端示例数据，生成、停用只影响这一页。
- Mock API 只认写死的 `KANGFU-2026`，后台生成的新码在手机端一定提示“邀请码不对”。
- 手机端验证只是和本地常量比较，没问过服务端，过期、用完、停用都感知不到。
- 后台显示的使用次数不会因为手机端有人入团而变化，两个端看到的是两份账。

这一版做四件事：

1. Mock API 新增邀请码种子和 `/api/invites` 接口，统一计算可用、已用完、已过期、已停用。
2. 社团后台邀请码页改接共享接口，生成、复制、停用都写回 Mock API；列表每 5 秒自动刷新。
3. 手机端“验证邀请码”改为调用服务端，成功后才进入资料页；停用、过期、用完直接显示服务端返回的原因。
4. 新成员提交申请时，服务端再次校验邀请码，并在真正创建成员时把使用次数加一；用同一用户名重新提交被拒绝的申请，不重复占用名额。

仍然不做：真实登录和会话、短信/邮件邀请、邀请码编辑和删除、按班级绑定、防刷限流、操作审计、审批通过后才占用名额。

## 2. 邀请码模型

邀请码存在 Mock API 的 `state.invites` 里：

```ts
type InviteStatus = 'active' | 'used' | 'expired' | 'disabled';

interface InviteCode {
  id: string;        // inv-001
  code: string;      // KANGFU-2026 / QINGRUN-5064
  note: string;      // 用途备注
  createdAt: string;
  expiresAt: string;
  maxUses: number;
  usedCount: number;
  disabled: boolean;
  status: InviteStatus; // 接口计算，不落库
  remaining: number;    // maxUses - usedCount，最小为 0
}
```

状态按下面的顺序计算，先命中先返回：

| 优先级 | 条件 | 状态 | 手机端提示 |
| --- | --- | --- | --- |
| 1 | `disabled === true` | `disabled` 已停用 | 这个邀请码已停用，请向社长要一个新的邀请码。 |
| 2 | `expiresAt` 早于当前时间 | `expired` 已过期 | 这个邀请码已过期，请向社长要一个新的邀请码。 |
| 3 | `usedCount >= maxUses` | `used` 已用完 | 这个邀请码已经用完了，请向社长要一个新的邀请码。 |
| 4 | 以上都不满足 | `active` 可用 | 验证通过，进入资料页 |

先判断停用、再判断过期、最后判断用完，是为了让后台显示最接近操作事实的原因：一个既过期又用满的码显示“已过期”，而不是“已用完”；社长手动停用的码始终显示“已停用”。

种子有 4 个邀请码：

| 邀请码 | 用途 | 上限 | 已用 | 有效期 | 初始状态 |
| --- | --- | --- | --- | --- | --- |
| `KANGFU-2026` | 演示邀请码（可直接分享） | 30 | 3 | 30 天后 | 可用 |
| `QINGRUN-1101` | 高一（3）班专场 | 10 | 7 | 8 天后 | 可用 |
| `QINGRUN-1015` | 校运会招募 | 20 | 20 | 1 天前 | 已过期 |
| `QINGRUN-0920` | 开学季体验码 | 30 | 18 | 5 天前 | 已停用 |

按种子计算，后台首屏是：4 个邀请码、2 个可用、累计使用 48 次、总名额 90、已停用 1 个。过期码不计入“已停用”，因为它不是社长手动停的。

## 3. 接口

邀请码接口和其他共享数据一样挂在 `/api` 下：

| 方法 | 路径 | 请求 | 返回 | 说明 |
| --- | --- | --- | --- | --- |
| GET | `/api/invites` | 无 | `InviteCode[]` | 按可用 → 已用完 → 已过期 → 已停用排序，同状态按创建时间倒序 |
| POST | `/api/invites` | `{ note, maxUses, expiresInDays }` | `InviteCode`，201 | 生成 `QINGRUN-四位数字`，自动查重 |
| POST | `/api/invites/validate` | `{ code }` | `{ ok: true, invite }` | 失败返回 400 和中文原因 |
| PATCH | `/api/invites/:id` | `{ status: 'disabled' }` | `InviteCode` | 目前只支持停用 |
| POST | `/api/member-applications` | `{ inviteCode, nickname, username, grade }` | `{ application, member }`，201 | 入团申请，服务端再次校验邀请码 |
| GET | `/api/member-applications/:id` | 无 | `MemberApplication` | 手机端轮询审批结果 |

生成规则：

- `maxUses` 必须是 1–100 的整数，`expiresInDays` 必须是 1–90 的整数。
- `note` 为空时写“成员邀请”，最长保留 40 个字符。
- 邀请码形如 `QINGRUN-5064`，生成时与现有码逐一比较，重复就重抽。
- 新码的 `usedCount` 为 0，有效期从生成日 23:59 起算。

校验规则：

- 邀请码大小写不敏感，前后空格会去掉。
- 不在表里：`邀请码不对，请向社长要一个新的邀请码。`
- 停用、过期、用完分别返回上表中的三种提示，不再统一说“邀请码错误”。
- 校验成功只返回可公开字段和剩余次数，不返回其他社团信息。

占用规则：

1. 新成员提交申请成功时，`usedCount` 加一，最多加到 `maxUses`。
2. 同一个用户名被拒绝后重新提交，只更新原成员记录，不再加一。
3. 提交失败（昵称、用户名、年级不合法，或邀请码在提交时已经失效）不占用名额。
4. 当前是在“提交申请”时占用，不是“审批通过”时占用；被拒绝不会返还名额。这是这一版的已知取舍，正式版需要决定是审批通过后占用，还是拒绝时返还。

`/api/health` 和 `/api/reset` 都会返回 `invites` 数量，方便脚本确认种子是否恢复。

## 4. 社团后台

邀请码页仍然是原来的位置：侧栏「邀请码」。

- 统计卡：可用邀请码、累计使用、名额上限、已停用。
- 表格：邀请码、用途、有效期、使用情况、状态、操作。
- 每行可以复制邀请码；只有“可用”状态显示“停用”。
- 生成弹窗：用途备注、最多使用次数（1–100）、有效期（1–90 天）。
- 停用确认：写清“已经通过它加入的成员不受影响”。
- 页面每 5 秒重新拉取一次，手机端用掉一次后，后台不必手动刷新就能看到 `1 / 2` 这样的变化。

后台的共享接口在 `admin/src/data/inviteApi.ts`：

```ts
inviteApi.listInvites()
inviteApi.createInvite({ note, maxUses, expiresInDays })
inviteApi.disableInvite(id)
```

`InviteStatus` 增加了 `used`，后台显示为“已用完”。邀请码页不再引用 `admin/src/data/index.ts` 的本地 repository。

## 5. 手机端

入团仍然从登录页的「我有邀请码」进入，但验证步骤变成异步：

1. 输入邀请码，点「验证邀请码」。
2. 按钮进入「正在验证…」并禁用，避免连点。
3. 服务端通过后进入资料页，填写昵称、年级、用户名。
4. 点「提交入团申请」时，服务端再次校验邀请码；如果这期间码被停用或用完，会显示对应原因，不创建成员。
5. 提交成功后进入待审批页，每 2.5 秒查询一次审批结果。

错误提示直接使用服务端文案，手机端不再维护另一套判断。验证码为空时在本地提示：“请先填写社长给你的邀请码。”

登录页仍保留「填入演示邀请码 KANGFU-2026」快捷入口，方便没有后台在场的演示；它和手动输入走同一个接口，不是写死的旁路。

## 6. 验收

新增跨端脚本 `verify-invites.mjs`，同时控制手机端（390×844）和社团后台（1440×1000），共 44 项断言，最终 44/44、退出码 0、无 console error / warning。

覆盖的真实流程：

1. 重置后 Mock API 返回 4 个邀请码、2 个可用、12 名成员。
2. 后台登录，邀请码页显示 4 条记录。
3. 后台生成「联调邀请码」，最多 2 次、7 天有效，得到 `QINGRUN-5064`。
4. 手机端输入这个码，验证通过并进入资料页。
5. 填写「邀请测试 / 高二 / invitetest」，提交申请，进入待审批页。
6. API 中该码变为 `usedCount: 1`、`remaining: 1`，成员变为 13 人，申请备注包含实际使用的码。
7. 后台 5 秒内刷新为 `1 / 2`，累计使用从 48 变为 49。
8. 后台停用该码，手机端再次验证时显示“这个邀请码已停用，请向社长要一个新的邀请码。”
9. 测试结束重置，恢复 4 个邀请码、12 名成员。

## 8. 边界与下一步

这一版仍然是本地原型，邀请码不是安全凭证：

- 邀请码明文显示、明文传输，没有加密、签名或一次性令牌。
- 没有真实账号、登录会话、设备绑定或防刷；任何人拿到码都能提交申请。
- 没有按班级/学校绑定，也没有邀请码编辑、删除、重新生成和导出。
- 没有操作审计，谁生成了码、谁停用了码都只存在当前进程内存。
- 拒绝申请不返还名额，审批通过前就占用了名额。
- 刷新浏览器会回登录页，重启 Mock API 或点“重置演示数据”会回种子。
- 手机端提交成功后的成员仍使用 `m-001` 的活动、消息和成长数据，不是独立成员档案。

下一步可以继续补：

1. 挑战手机端参与与进度同步，让后台创建的挑战真正出现在成员端。
2. 跑步记录跨端，让社团后台“记录与导出”读到手机端保存的记录。
3. 邀请码审批通过后占用、拒绝返还，以及生成/停用审计。
