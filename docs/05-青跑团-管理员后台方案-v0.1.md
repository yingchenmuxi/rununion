# 青跑团 · 管理员后台方案 v0.1

- 日期：2026-11-17
- 状态：技术方案，尚未开发
- 依据：docs/03-青跑团-功能设计-v0.1.md、docs/04-青跑团-页面流程与线框-v0.1.md
- 说明：这份文档只讲“后台怎么搭”，不写代码，不改现有原型。

## 0. 一句话结论

管理员后台是一个**电脑浏览器打开的网页**，和手机 App 共用一个数据库。

第一版不要从零造后台。推荐：

- 用 **PocketBase** 做后端：数据库、账号、API、文件存储、自带管理面板。
- 用 **React + Vite + TypeScript** 做一个简单的社长后台，只做 6 个页面。
- 手机 App 和社长后台都调用同一套 PocketBase API。
- PocketBase 的“超级管理员”只留给你自己/技术维护，不交给社长。

这样既能快速跑通，又不会把权限做乱。

## 1. 后台给谁用

| 角色 | 在哪里用 | 能做什么 | 不能做什么 |
|---|---|---|---|
| 平台管理员 | 电脑 Web | 开通社团、指定社长、重置社长密码、停用社团、看平台审计 | 不做社团日常审批，不看成员私密记录 |
| 社长（owner） | 电脑 Web | 审批成员、发邀请码、发公告、建线上挑战、看社团可见记录、导出 | 不能创建社团，不能看成员私密记录，不能改别人的跑步记录 |
| 成员 | 手机 App | 加入社团、记录跑步、看自己的成长、看社团动态/公告/挑战 | 不能登录后台 |

关键点：

- 后台不是手机 App 里的一个标签页。
- 社长和平台管理员是两种账号，权限不同。
- 成员没有后台账号。

## 2. 第一版只做 6 块

docs/04 写了 11 节后台页面，但开发不要一次全做。第一版先做 6 块：

| 序号 | 页面 | 先做什么 | 为什么先做 |
|---|---|---|---|
| 1 | 登录 + 概览 | 社长登录、待审批数、成员数、本周总跑量 | 一进来知道今天要处理什么 |
| 2 | 成员 | 批准、拒绝、移出、重置密码 | 入团流程的核心 |
| 3 | 邀请码 | 新建、复制、停用 | 成员怎么进来 |
| 4 | 公告 | 新建、编辑、删除、置顶 | 社团通知 |
| 5 | 挑战 | 新建、提前结束、看参加/完成人数 | 第一版唯一的“活动” |
| 6 | 记录 + 导出 | 只看社团可见记录、导出 CSV | 社长需要看社团情况 |

审计日志从第一天就写，但“审计页面”可以最后补。
社团设置页面也最后补，第一版社团资料由平台管理员开通时填好。

## 3. 技术选型

### 3.1 为什么用 PocketBase

PocketBase 适合这个阶段：

- Windows 上就是一个可执行文件，双击/命令行就能跑。
- 自带 SQLite 数据库，不需要另装 MySQL/PostgreSQL。
- 自带账号/密码登录、Token、REST API。
- 自带一个管理面板，方便你看数据、改字段、排查问题。
- 数据量 30–50 人完全够用；以后要迁 PostgreSQL 再说。
- 开源，代码和数据都在自己服务器上。

它不适合的地方：

- 自带管理面板是给开发者/超级管理员用的，不是给社长用的。
- 复杂的业务规则、审计、导出，需要自己写一点服务端逻辑。
- 以后社团变多、数据变大，可能要换 PostgreSQL 或加缓存；V0.1 不用提前操心。

### 3.2 目录结构

    E:\QPTapp\
      mobile\        现有 Expo 手机端/网页原型
      server\        PocketBase 后端（单文件 + pb_data）
      admin\         社长后台（React + Vite）
      docs\          设计文档

### 3.3 请求关系

    手机 App（成员）
          \
           \  REST API + 成员 token
            \
             PocketBase（数据库 + 权限规则 + 自定义接口）
            /
           /  REST API + 社长 token
          /
    社长后台（电脑 Web）

平台管理员也用电脑 Web，但用另一种账号和权限。

### 3.4 端口建议

本地已有 Expo 静态服务占用 8090，建议：

- PocketBase：8091
- 社长后台：5173
- Expo 开发服务：8081

端口可以改，只要不冲突。

## 4. 数据表（第一版）

表名可以按 PocketBase 习惯调整，但字段含义不要变。

### users（成员/社长/平台管理员）

- username：全局唯一
- nickname：显示名
- password：PocketBase 加密存储
- role：member / owner / platform_admin
- club_id：所属社团；平台管理员可为空
- age_group：14–15 / 16–17 / 18–20
- gender：male / female / private
- city、district
- weekly_goal_km
- bio
- default_visibility：club / private
- show_weekly_stats：boolean
- status：pending / active / rejected / removed / left / disabled
- must_change_password：boolean

### clubs

- name、city、district
- description
- training_place
- owner_id
- status：active / disabled

### club_members

如果 users 里已经有 club_id，这张表可以先用 users 代替；但社团变多后建议独立：

- club_id
- user_id
- role：owner / member
- status：pending / active / removed / left
- joined_at

### invite_codes

- code：6 位大写字母/数字
- club_id
- created_by
- expires_at
- max_uses
- used_count
- active

### run_records

- user_id
- club_id
- run_date
- distance_km
- duration_seconds
- pace_seconds_per_km
- feel：1–5
- note
- visibility：club / private
- created_at、updated_at

### announcements

- club_id
- title
- body
- pinned
- created_by
- created_at

### challenges

- club_id
- title

- start_date、end_date
- target_type：count / distance

### challenge_participants

## 5. 权限矩阵

这是后台最容易被忽略、但最重要的部分。不能只靠页面隐藏，必须让服务端也拦住。

| 操作 | 成员 | 社长 | 平台管理员 | 超级管理员 |
|---|---|---|---|---|
| 看自己的私密记录 | 可以 | 不可以 | 不可以 | 技术上可以，但只做技术维护 |
| 看本社团“社团可见”记录 | 可以 | 可以 | 不可以 | 技术上可以 |
| 改自己的记录 | 可以 | 不可以 | 不可以 | 不用于日常 |
| 审批本社团成员 | 不可以 | 可以 | 不可以 | 不用于日常 |
| 发本社团邀请码 | 不可以 | 可以 | 不可以 | 不用于日常 |
| 发本社团公告 | 不可以 | 可以 | 不可以 | 不用于日常 |
| 建本社团挑战 | 不可以 | 可以 | 不可以 | 不用于日常 |
| 开通社团 | 不可以 | 不可以 | 可以 | 可以 |
| 重置社长密码 | 不可以 | 不可以 | 可以 | 可以 |
| 看平台审计 | 不可以 | 不可以 | 可以 | 可以 |

重要说明：

- PocketBase 的超级管理员能绕过 API 规则，看到所有数据。所以超级管理员只留给你自己/技术维护，不交给社长，也不拿来做日常运营。
- 平台管理员用普通账号 + 自定义后台；如果平台管理员必须“不能看私密记录”，就不能给他超级管理员。
- 社长只能看自己社团的“社团可见”记录；私密记录在 API 层就过滤掉。
- 导出 CSV 也在服务端过滤，不能靠前端隐藏。

## 6. 页面明细

### 6.1 登录 + 概览

登录：

- 用户名、密码。
- 首次登录/被重置密码后，强制改密码。
- 忘记密码：社长由平台管理员重置；成员由社长重置。
- 连续失败要限流。

概览卡片：

- 待审批人数
- 成员总数
- 本周社团总跑量
- 进行中挑战数

快捷入口：

- 去审批
- 生成邀请码
- 发公告
- 建挑战

### 6.2 成员

表格列：

- 昵称、用户名、年龄段、状态、加入时间、本周跑量（允许展示时）

筛选：

- 待审批 / 正常 / 已移出
- 搜昵称/用户名

操作：

- 批准
- 拒绝
- 移出社团（二次确认）
- 重置密码（临时密码只显示一次）
- 导出当前筛选结果

规则：

- 不能看私密记录。
- 不能改成员资料/跑步记录。
- 不能把成员设为管理员；V0.1 只有 owner 一个管理员。

### 6.3 邀请码

列表：

- 邀请码、创建人、创建时间、有效期、已用/上限、状态

操作：

- 新建：有效期 1/7/30 天，使用上限默认 50
- 复制
- 停用

规则：

- 6 位大写字母/数字。
- 过期/用完自动失效。
- 邀请码只对应一个社团。

### 6.4 公告

列表：

- 标题、作者、置顶、发布时间

操作：

- 新建、编辑、删除、置顶
- 删除二次确认

规则：

- 正文纯文本，最多 2000 字。
- 成员只读，不能评论。

### 6.5 挑战

列表：

- 标题、日期、目标、参加人数、完成人数、状态

新建字段：

- 标题、说明、开始/结束日期、目标类型（次数/距离）、目标值

操作：

- 创建
- 编辑（未开始）
- 提前结束
- 看参加/完成人数

规则：

- 不显示排名。
- 参与者列表按加入时间，不按成绩。
- 进度由“社团可见”的跑步记录自动算；私密记录不计入。
- 挑战结束后只读，补录不再计入。

### 6.6 记录 + 导出

记录页：

- 只显示本社团“社团可见”记录。
- 列：成员昵称、日期、距离、时长、配速、感受。
- 可筛选日期/成员。
- 不能编辑/删除。

导出：

- 成员 CSV
- 跑步记录 CSV
- 日期范围
- 不含私密记录
- 导出动作写审计日志

## 7. 本地怎么跑

第一版本地开发，不碰公网真实未成年人数据。

步骤概念：

1. 下载 PocketBase Windows 版，放到 server/。
2. 启动：

    pocketbase serve --http=127.0.0.1:8091

3. 打开启动日志里的管理面板地址，创建集合/字段。
4. 创建 admin/：

    npm create vite@latest admin -- --template react-ts

5. 安装 PocketBase JS SDK，配置 API 地址为 http://127.0.0.1:8091。
6. 先做登录 + 成员审批两个页面，跑通再往下做。

注意：

- 不要用真实成员数据做公网测试。
- PocketBase 的 pb_data 要备份。
- 本地开发时，手机访问电脑要用局域网 IP，不是 localhost；这个等手机端联调再处理。

## 8. 部署与安全

上线前至少做到：

- HTTPS（Nginx 反向代理 + 证书）。
- 后台地址不公开宣传；能加 IP 白名单就加。
- 超级管理员强密码；不和社长账号共用。
- 登录限流；失败次数过多锁定/延迟。
- 每天备份 pb_data；至少保留 7 天。
- 服务器防火墙只开必要端口。
- 审计日志只增不改；导出也要记。
- 隐私政策、用户协议、备案信息齐全。
- 真实未成年人数据不放在测试环境。

Windows 服务器可以用 NSSM 把 PocketBase 注册成服务，开机自启；具体等要部署时再配。

## 9. 开发顺序

建议按这个顺序，不要一次做全：

1. 先定后台线框（不写代码）。
2. 本地跑起 PocketBase，建表、设权限规则。
3. 做登录 + 概览。
4. 做成员审批 + 邀请码。
5. 做公告 + 挑战。
6. 做记录查看 + CSV 导出 + 审计。
7. 手机端接 API，用两个账号测私密记录。
8. 最后再部署到服务器。

## 10. 明确不做

- 不做手机管理端。
- 不做多管理员/角色转移。
- 不做复杂图表/大屏。
- 不做消息推送。
- 不做支付。
- 不做平台管理员“看私密记录”的功能。
- 不把 PocketBase 自带管理面板直接给社长用。

## 11. 待确认

这份方案依赖 docs/04 第 9 节的 10 条默认规则，尤其是：

- 私密记录不计入社团汇总/挑战。
- 退出/被移出后记录转私密。
- 社长不能直接退出。
- 一个账号只能加入一个社团。

你确认这 10 条后，我建议下一步先画“社长后台 6 页线框”，确认后再搭本地 PocketBase。这样不会白写代码。
