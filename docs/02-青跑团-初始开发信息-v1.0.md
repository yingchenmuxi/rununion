# 青跑团 · 初始开发信息 v1.0

> 实现状态（2026-11-19）：跑步记录已实现 GPS / 截图确认 / 文件导入三通道，见 [开跑记录与成长同步 v0.2](10-开跑记录与成长同步-v0.1.md)；文中“第一版不采集 GPS”已被取代。

> 状态：可执行草案，等待创始人确认第 10 节的 6 个决策
> 日期：2026-11-16
> 适用阶段：单校试点 → 同城复制 → 省级连线
> 一句话：让每一个想跑下去的青少年，都能找到同伴、方法和舞台。

## 0. 先看结论

青跑团不是“再做一个跑步 App”，而是一个以跑团为节点、以成长记录为底座、以公益为底色的青少年长跑共同体。

第一版不要六个功能一起上。先在一所学校跑通三个闭环：

1. **加入**：学校跑团入驻 → 邀请码 → 监护人同意 → 成为成员。
2. **记录**：手动或计时记录 → 成长档案 → 团队成长榜。
3. **活动**：发布活动 → 报名 → 签到 → 记录与徽章。

第一版暂不做：全国个人速度总榜、AI 问答、陌生人 1 对 1 匹配、跨省接力、现金捐赠、实时 GPS 轨迹、原生 iOS。

原因不是这些功能不重要，而是：

- **供给密度**：没有真实的学校和跑团，榜单、匹配、接力都是空转。
- **安全**：未成年人产品，线下活动和社交的风险远高于写代码的风险。
- **数据质量**：没有可信的记录，排名和成长档案没有意义。
- **你的时间**：一个人做开发，必须先把一个学校跑通，再复制。

## 1. 产品定义

### 1.1 用户与角色

| 角色 | 他们是谁 | 他们真正要什么 | 第一版是否需要 |
|---|---|---|---|
| 青少年跑者 | 10–20 岁，刚开始跑或已在校队/跑团 | 被看见、有同伴、别受伤、能坚持 | 是 |
| 家长/监护人 | 孩子的安全与时间守门人 | 安全、透明、不耽误学习 | 是（同意与查看） |
| 体育老师/跑团负责人 | 学校社团、民间跑团的组织者 | 招人、管活动、留人、被认可 | 是 |
| 教练 | 体育老师、田径教练、资深跑者 | 输出经验、获得尊重 | 第二版 |
| 学校管理员 | 学校体育组/德育处 | 安全、成果、可交代 | 是（只读聚合数据） |
| 平台管理员 | 你和早期团队 | 审核、风控、运营 | 是 |
| 公益伙伴 | 基金会、慈善组织、企业 | 合规、透明、真实故事 | 第三版 |

### 1.2 要解决的真问题

1. **不会跑**：初跑者缺科学方法，容易受伤、放弃。
2. **没人陪**：长跑孤独，青少年尤其需要同伴和正向压力。
3. **跑团散**：各地跑团各自摸索，缺工具、缺连接、缺资源。
4. **没记录**：孩子的坚持没有被好好留存，只有比赛名次。
5. **有门槛**：有天赋但家境困难的孩子，缺装备、名额和指导。

### 1.3 价值主张

- 对青少年：不追速度，记录每一次坚持；找到同城同水平的伙伴。
- 对老师/团长：一套现成的成员、活动、里程和成长管理工具。
- 对家长：看得见的安全规则、隐私控制和活动同意流程。
- 对学校：可展示的体育成果，但不暴露学生个人隐私。
- 对公益伙伴：真实、可核验的青少年跑步故事和需求。

### 1.4 产品原则

- **安全 > 增长**：未成年人产品，安全是第一条产品需求。
- **成长 > 竞速**：记录坚持，不用名次定义孩子。
- **真实 > 热闹**：只认有证据的成绩；宁可榜单小，不要数据假。
- **供给先行**：先让跑团用起来，再让个人用户进来。
- **小切口**：一所学校、一个跑团、几百个孩子，跑通再复制。
- **公益底色**：早期不靠抽成、广告和现金捐赠赚钱。

## 2. MVP 范围

### 2.1 P0：第一版必须有

| 功能 | 必须做到的验收标准 | 第一版边界 |
|---|---|---|
| 学校/跑团入驻 | 老师提交学校、跑团、负责人、场地、安全承诺；平台人工审核；生成跑团邀请码 | 不做开放注册；先人工审核 |
| 邀请码加入与角色 | 学生用邀请码加入；角色分为学生、团长、教练、学校管理员、平台管理员 | 试点期由老师预建账号，减少短信成本 |
| 监护人同意 | 记录同意人、关系、同意范围、版本、时间；可撤回；未满 14 岁使用单独儿童规则 | 纸质+线上录入都支持；不收集身份证号 |
| 活动发布/报名/签到 | 团长发布时间、地点、距离、人数、年龄、保险、急救安排；学生报名；监护人确认；现场签到 | 不做支付；不做跨校大型赛事 |
| 跑步记录 | 日期、距离、用时、感受、可见性；手动录入 + 计时器；可关联活动 | 第一版不采集 GPS；距离可手动填 |
| 成长档案 | PB、月跑量、连续周数、徽章、参赛经历；默认仅自己可见 | 不做公开个人速度榜 |
| 团队成长榜 | 按参与率、总里程、进步幅度、完赛人数展示；不按个人绝对速度 | 先做校级/俱乐部级 |
| 经验库 | 人工精选训练、热身、恢复、伤病预防内容；可搜索；标注作者与来源 | 不做 AI 问答；不做医疗诊断 |
| 安全中心/举报 | 隐私设置、活动安全须知、紧急联系人、举报入口、拉黑 | 举报必须有人工处理 |
| 管理后台 | 审核跑团/活动/文章/举报；查看聚合数据；导出 | 先做网页端最小后台 |

### 2.2 P1：试点跑通后

- 同城跑团地图与加入申请。
- 教练问答（人工回答，不是 AI）。
- AI 经验检索：只基于已审核文章，必须给出来源，不提供诊断。
- 同城/同水平跑友匹配：先做“活动搭子”，不做陌生人私聊。
- 家长查看：只看参与、活动、安全信息，不看孩子私密记录。
- 活动照片、电子证书、徽章。
- 站内消息/订阅通知。

### 2.3 P2：有供给和运营能力后

- 金字传驿跨年省级 100 公里接力。
- 公益助跑帮扶。
- 区/市/省/全国四级榜单。
- 支付、捐赠、赞助。
- 实时 GPS、轨迹、直播。
- 原生 iOS 与 App Store 上架。

### 2.4 明确不做的边界

- **不收集身份证号**：第一版不做身份证实名；如后续赛事或法规要求，再单独设计最小化实名方案。
- **不公开精确位置**：只显示城市/区/学校；活动地点在报名且同意后可见。
- **不做全站陌生人私信**：先团内、活动内沟通。
- **不直接收现金**：公益只做物资、名额、教练时间；现金必须与有公募资格的机构合作。
- **不记录体重、体脂、外貌评价**：避免身材焦虑。
- **不鼓励未成年人跑全马**：全马只做个人记录，需教练/监护人确认，不进入未成年人竞速排名；榜单以 1500 米–半马为主。
- **不做医疗诊断**：经验库内容必须标注“非医疗建议”，伤病问题引导就医。
- **不做无监护人的夜间/跨城活动**：线下活动必须有负责人、急救方案和监护人同意。

## 3. 核心流程

### 3.1 跑团入驻

1. 体育老师/团长填写：学校、跑团名称、城市/区、负责人、联系方式、场地、预计人数、安全承诺。
2. 上传学校同意函或教师证明（试点期必须）。
3. 平台人工审核（1–3 个工作日）。
4. 审核通过，生成跑团主页和邀请码。
5. 学校管理员账号只能看聚合数据，不看学生个人记录。

### 3.2 学生加入与监护人同意

1. 学生下载 App，输入学校/跑团邀请码。
2. 填写昵称、出生年份/年龄组、性别（可不愿公开）、城市；不填真实姓名、学校班级可后填。
3. 阅读未成年人隐私规则；未满 14 岁走单独儿童规则。
4. 监护人同意：纸质签字拍照上传，或监护人手机端确认；记录同意版本和范围。
5. 加入成功；默认昵称展示、记录仅自己/跑团可见。
6. 监护人可随时撤回同意；撤回后账号转为受限/删除。

### 3.3 记录跑步

1. 选择“计时跑”或“手动记录”。
2. 计时跑：开始/结束，记录用时；第一版距离手动填，不采集 GPS。
3. 手动记录：日期、距离、用时、感受、是否活动。
4. 选择可见性：仅自己 / 跑团 / 公开（默认仅自己）。
5. 保存后计入团队里程；PB 需单独填写，可选择“活动认证/赛事认证”。
6. 记录可编辑/删除；已用于榜单的记录保留审计痕迹。

### 3.4 活动发布与报名

1. 团长创建活动：时间、地点、距离、人数上限、年龄范围、是否需监护人、保险、急救、天气预案。
2. 平台审核（第一版全部人工）。
3. 学生报名；未成年人需监护人确认。
4. 活动当天签到；未签到不影响信用，但记录“未到场”。
5. 活动结束后，参与记录可一键归集到成长档案；颁发徽章/证书。

### 3.5 成长与榜单

- 个人：PB、月跑量、连续周数、徽章、参赛经历；默认私密。
- 团队：参与率、总里程、进步幅度、完赛人数；不展示个人绝对速度排名。
- 成绩可信度：自己填写 / 活动认证 / 赛事认证；榜单只认后两种。
- 年龄组：10–12、13–15、16–18、19–20；男女组；不愿公开性别可不进榜。
- 四级榜单：先做校级，区/市/省/全国在供给足够后逐级开放。

### 3.6 经验库

1. 用户/教练提交文章：标题、标签、正文、来源、作者身份。
2. 平台审核：是否科学、是否有广告、是否涉及医疗诊断、是否适合未成年人。
3. 发布；标注“经验分享，非医疗建议”。
4. 搜索按标签/距离/场景；AI 检索在 P1，只基于已审核内容并给出来源。
5. 教练问答单独入口，人工回答；不承诺即时。

### 3.7 安全与举报

- 每条 UGC 内容有举报入口。
- 举报类型：隐私泄露、骚扰、虚假成绩、危险训练建议、广告、其他。
- 管理员 24 小时内初核（试点期承诺，不冒充法律时限）。
- 严重情况：隐藏内容、限制账号、联系学校/监护人、必要时报警。
- 所有处理写审计日志。

## 4. 页面与信息架构

当前原型是五个底部标签：

| 标签 | 当前内容 | 后续子页面 |
|---|---|---|
| 首页 | 本周跑量、快捷入口、我的跑团、本周活动、成长摘要、经验库 | 通知、活动详情、文章详情 |
| 跑团 | 当前跑团、同城跑团、近期活动、入驻流程 | 跑团主页、成员、活动发布、加入申请 |

## 5. 数据模型

所有表建议包含：id、created_at、updated_at、deleted_at（软删除）。用户主键用 UUID，不用自增 ID 暴露规模。

| 实体 | 关键字段 | 说明 |
|---|---|---|
| users | id, nickname, birth_year, age_group, gender, city, school_id, avatar_url, role, status | 不存身份证号；性别可选“不愿公开” |
| guardian_consents | id, user_id, guardian_name, relation, phone, scope, version, signed_at, revoked_at, evidence_url | 同意范围要具体；版本化 |
| schools | id, name, city, district, address_level, contact, status | 地址只到学校，不存家庭住址 |
| clubs | id, school_id, name, type, city, district, leader_id, description, status, invite_code | 学校社团/民间跑团/社区跑团 |
| club_members | club_id, user_id, role, status, joined_at | 角色：学生/团长/教练/管理员 |
| activities | id, club_id, title, start_at, place, distance_km, capacity, min_age, max_age, requires_guardian, insurance_note, emergency_plan, status | 第一版全部人工审核 |
| activity_signups | activity_id, user_id, status, guardian_consent_id, checked_in_at | 报名/候补/取消/签到 |
| run_records | id, user_id, club_id, activity_id, run_date, distance_km, duration_sec, pace_sec, feel, visibility, source, verified_level, note | source: manual/timer；verified: self/activity/race |
| pb_records | id, user_id, distance, result_sec, event_name, event_date, verified_level, evidence_url | 1500m/3K/5K/10K/半马/全马 |
| badges | id, name, description, rule_json, icon | 徽章规则可配置 |
| user_badges | user_id, badge_id, awarded_at, source | 活动/里程/连续周 |
| articles | id, author_id, type, title, summary, content, tags, source, status, reviewed_by | 经验库；审核后发布 |
| reports | id, reporter_id, target_type, target_id, reason, detail, status, handled_by | 举报与处理 |
| admin_audit_logs | id, admin_id, action, target_type, target_id, before_json, after_json | 管理操作留痕 |
| match_profiles | user_id, city, pace_range, distance_pref, visibility | P1；默认关闭 |
| help_requests | id, user_id, need_type, story, status, handled_by | P2；不直接收钱 |
| relay_events / relay_teams / relay_legs | event_id, province, team_id, leg_no, distance_km, result | P2；金字传驿 |

关系要点：

- 一个学校可有多个跑团；一个学生第一版只加入一个主跑团。
- 活动属于跑团；报名属于用户；未成年人报名必须绑定有效监护人同意。
- 跑步记录可关联活动；关联后可信度可升级为 activity。
- 经验库文章必须有人工审核记录；AI 检索只读已发布文章。

## 6. 技术方案

### 6.1 当前原型

- Expo SDK 58、React Native 0.88、TypeScript、Expo Router。
- 五个主页面：首页、跑团、开跑、成长、我的。
- 已有登录/入团演示流程：邀请码、资料填写、待社长审批、演示通过、退出登录。
- 手机端为本地内存演示数据，管理后台为前端示例数据；尚无真实后端、真实账号或真实用户数据。
- 管理后台已有登录、概览、成员、邀请码、公告、挑战、记录与导出页面。
- Web 导出可运行；Android 真机还没验证。
- 命令见根目录 README。

### 6.2 目标架构

    Expo App（Android / Web）
            │ HTTPS
            ▼
    境内 API 服务（鉴权、业务规则、审核）
            │
            ├── PostgreSQL / SQLite（业务数据）
            ├── 对象存储（活动照片、文章封面）
            └── 管理后台（Web）

第一版不接第三方统计 SDK；未成年人产品尽量少留痕。

### 6.3 分阶段建议

**阶段 A：原型（现在）**

- 继续用本地 mock 数据，把页面和流程走通。
- 抽出一层 api 接口，页面不直接写死数据，方便以后换后端。
- 不录入任何真实未成年人信息。

**阶段 B：单校试点**

- 用你已有的境内服务器，部署 HTTPS、数据库、文件存储、每日备份。
- 对新手最省事的方案：PocketBase（单文件、自带 Auth/数据库/文件/后台）先跑试点；数据量上来后迁移 PostgreSQL。
- 更可控的方案：Node/NestJS + PostgreSQL + 对象存储；需要更多开发时间。
- 无论哪种，先做到：邀请码登录、角色权限、监护人同意、活动报名、记录、审核、备份、日志。
- 真实未成年人数据不要放在境外免费套餐；开发演示可以用假数据。

**阶段 C：同城复制**

- PostgreSQL + 独立 API；对象存储；队列；监控；数据导出。
- 管理后台补审核队列、举报处理、学校/跑团管理。
- 再评估是否需要小程序/H5 双端。

### 6.4 登录与同意

- 试点期：老师预建账号 + 一次性邀请码 + 自设密码；避免短信费用。
- 正式期：手机号验证码/微信登录；监护人手机号单独验证。
- 监护人同意：纸质签字拍照上传，或监护人端在线确认；记录版本、范围、时间、撤回。
- 未满 14 岁：单独儿童隐私规则；不做个性化推荐；默认最严格可见性。

### 6.5 AI 经验库

- 先有 50–100 篇人工审核内容，再上 AI 检索。
- 服务端代理模型 API，key 不进客户端。
- RAG 只检索已审核文章；回答必须带来源链接。
- 明确“非医疗建议”；涉及伤病、用药、极端训练，直接建议就医/找教练。
- 不对未成年人做自动训练计划；不做排名预测。

### 6.6 地图与位置

- 第一版只存城市/区/学校，不存家庭住址。
- 同城地图 P1 再做；使用境内合规地图 SDK；只显示跑团/活动的大致位置。
- 活动集合点报名后才可见；不公开实时轨迹。

### 6.7 推送与统计

- 试点期用站内消息/微信群通知，不依赖推送。
- Android 国内推送链路复杂，等有运营需求再接。
- 统计只采集必要事件：加入、同意、记录、报名、签到、举报；不接广告 SDK。

### 6.8 安全底线

- 全站 HTTPS；管理员 2FA；最小权限；操作审计。
- 数据库每日备份，至少保留 7 天；定期做恢复演练。
- 敏感字段（监护人手机号）加密/脱敏展示。
- 注销与删除：用户可申请，30 天内处理；法律要求留存的做匿名化。
- 安全事件预案：发现、止损、通知、复盘。

## 7. 合规与安全

> 以下是产品设计建议，不是法律意见。公开上线前，请找属地律师/网信/教育/民政部门确认。

### 7.1 年龄分层与同意

| 年龄 | 同意要求 | 产品默认 |
|---|---|---|
| 未满 14 岁 | 监护人同意 + 单独儿童隐私规则 | 最严格隐私；不个性化推荐；不进公开榜 |
| 14–17 岁 | 监护人同意（注册与线下活动） | 默认团内可见；公开需再次确认 |
| 18–20 岁 | 本人同意 | 可选择公开 |

### 7.2 个人信息最小化

- 不收集身份证号、家庭住址、精确位置、人脸、指纹。
- 生日只存出生年份/年龄组；性别可选“不愿公开”。
- 监护人手机号只用于同意与紧急联系，不展示。
- 经验库不鼓励写个人伤病隐私；写经验用化名/脱敏。
- 不做“公开个人信息换功能”的默认勾选。

### 7.3 备案与文本

公开上线前至少准备：

- ICP 备案/APP 备案（按属地要求）。
- 隐私政策、用户协议、未成年人个人信息处理规则、监护人同意书。
- 内容审核与举报处理机制。
- 若涉及 AI 生成/推荐、算法推荐，按属地要求评估算法备案/安全评估。
- 若涉及公开募捐，必须与有公募资格的慈善组织合作，并依法公开信息。

### 7.4 线下活动安全

- 每场活动有负责人、急救包、紧急联系人、天气预案、路线说明。
- 未成年人活动需监护人同意；夜间/跨城/高强度活动提高审批级别。
- 建议购买活动责任险/意外险；具体险种与保额咨询保险机构。
- 教练/志愿者背景与资质审核；不与学生单独闭门相处。
- 事故处理流程：救人 → 通知监护人/学校 → 保留记录 → 复盘。

### 7.5 榜单与训练安全

- 不鼓励未成年人跑全马；全马只做个人记录，不进未成年人竞速榜。
- 不展示体重/体脂/外貌；不做“跑量越多越好”的连续打卡压力。
- 设置每周跑量提示、休息日提醒、伤病停跑建议。
- 成绩可信度分级；作弊处理先隐藏、再申诉、再公示规则。

### 7.6 公益与金钱

- 第一版不直接收现金、不做支付。
- 公益只做物资、名额、教练时间；如做现金，必须与有公募资格的机构合作，走对公账户，公开用途与票据。
- 不把“捐钱”与榜单/名额绑定，避免诱导未成年人消费。

## 8. 单校试点

### 8.1 试点目标

- 1 所学校、1 个跑团、30–50 名学生、4 周。
- 验证三件事：愿意加入并同意、愿意持续记录、老师愿意用后台办活动。
- 不追求全国用户、不追求榜单规模。

### 8.2 试点角色

- 你：产品、开发、运营、审核。
- 体育老师/团长：拉人、发活动、盯安全。
- 2 名学生志愿者：发通知、收集反馈。
- 1 名家长代表：看同意流程和隐私说明。
- 1 名教练/体育老师：审经验库内容。

### 8.3 四周节奏

| 周 | 重点 | 产出 |
|---|---|---|
| 第 0 周 | 学校书面同意、监护人同意书、账号导入、老师培训 | 30–50 个可用账号；同意台账 |
| 第 1 周 | 加入 + 第一次记录 | 加入率、首次记录率、问题清单 |
| 第 2 周 | 第一场活动 + 团队榜 | 活动报名/签到数据；老师反馈 |
| 第 3 周 | 经验库 + 第二次活动 | 3–5 篇精选内容；使用反馈 |
| 第 4 周 | 复盘 + 决策 | 试点报告；是否复制 |

### 8.4 试点指标

| 指标 | 目标 | 怎么算 |
|---|---|---|
| 邀请加入率 | ≥ 60% | 加入人数 / 被邀请人数 |
| 监护人同意完成率 | ≥ 80% | 完成同意 / 加入人数 |
| 首次记录率 | ≥ 70% | 至少 1 条记录 / 加入人数 |
| 周活跃记录率 | ≥ 50% | 每周至少 1 条记录 / 加入人数 |
| 4 周留存 | ≥ 40% | 第 4 周仍活跃 / 加入人数 |
| 活动数 | ≥ 2 场 | 完成签到 |
| 老师后台耗时 | ≤ 30 分钟/周 | 访谈估算 |
| 严重安全事故 | 0 | 事故记录 |
| 家长/学生反馈 | 正向为主 | 5 题问卷 + 访谈 |

### 8.5 试点前准备清单

- [ ] 学校书面同意（盖章/签字）。
- [ ] 体育老师/团长作为活动负责人。
- [ ] 监护人同意书模板（纸质+线上）。
- [ ] 隐私政策、未成年人规则、用户协议初稿。
- [ ] 活动路线、急救包、紧急联系人、天气预案。
- [ ] 保险方案（如学校已有覆盖，确认范围）。
- [ ] 境内服务器、HTTPS、备份、管理员账号。
- [ ] 演示数据与真实数据分离；试点前清空假数据。
- [ ] 反馈问卷与访谈提纲。
- [ ] 事故/举报处理人（你）与联系方式。

### 8.6 访谈问题

1. 你为什么不加入？是同意流程、隐私、还是没兴趣？
2. 你为什么不记录？忘了、麻烦、还是怕被比较？
3. 老师最花时间的一步是什么？
4. 家长最担心什么？看到什么会放心？
5. 如果只能保留一个功能，你选哪个？

## 10. 风险与待拍板

### 10.1 主要风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 学校不授权 | 无法进校 | 先找体育老师/班主任站台；书面同意；只做试点 |
| 监护人不同意 | 加入率低 | 纸质+线上两种；说明数据用途；默认隐私 |
| 线下活动事故 | 项目停摆 | 保险、急救、路线、天气、监护人同意、教练在场 |
| 虚假成绩 | 榜单失信 | 可信度分级；活动/赛事认证；抽查 |
| 内容危险/广告 | 伤害用户 | 人工审核；来源标注；举报；下架 |
| 未成年人沉迷/攀比 | 心理风险 | 不排名绝对速度；休息提醒；家长/教练参与 |
| 个人开发资源不足 | 延期 | 先做单校；用现成后端；不接大功能 |
| 数据泄露 | 严重信任危机 | 境内服务器、最小化、加密、备份、审计 |

### 10.2 需要你拍板的 6 件事

1. **试点学校**：是否就用你现在的高中？能否拿到体育老师/学校的书面同意？
2. **同意方式**：监护人纸质签字拍照，还是监护人手机端在线确认？谁负责收集？
3. **活动安全**：第一场活动是否买保险？学校是否已有覆盖？谁做急救负责人？
4. **数据托管**：试点是否用你现有的境内服务器？服务器系统/配置/能否装 Docker？
5. **首批内容**：你能否提供 3–5 篇真实训练/康复经验，或 1–2 位教练联系人？
6. **榜单边界**：第一版是否接受“只做团队成长榜，不做个人速度总榜”？全马是否只记录不排名？

### 10.3 接下来 3 个动作

1. 你确认上面 6 件事，尤其是试点学校和同意方式。
2. 我根据你的选择，做“邀请码加入 + 监护人同意 + 活动报名”的可点击流程。
3. 流程确认后，再接境内后端和真实账号；在此之前不录入真实未成年人信息。
